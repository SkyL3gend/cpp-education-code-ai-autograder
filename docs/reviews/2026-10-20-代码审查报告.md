# 项目代码审查报告

审查日期：2026-10-20\
被审版本：`pyproject.toml` 标记的 0.5.1（当前工作区）\
依据：原任务书，以及《双模式测评系统架构与实施方案》v0.2，特别是用户确认的“参考基准判断程序的方法，再为目标程序生成完整判断程序”。

## 1. 结论

CLI、Web、题库、协议、断言引擎和报告已经形成可展示的原型。但当前模式二主要实现为“模型生成菜单脚本或函数驱动，选择几个手写提取器，随后执行断言”，尚未完整实现“学习基准测试方法 → 迁移方法 → 验证目标判断程序”的设计。

现在最需要修正的是判定可信度：部分提取器把输入数据当成实际观测；适配覆盖和校准门禁不足；生成代码编译失败会直接归责学生。这些问题可能造成错误通过、错误失败，即使页面正常、现有测试通过也无法排除。

本次没有修改业务代码。新增本报告、只读复现脚本及其结果文件，便于后续模型按证据修复。

优先级：P1 表示在接收真实不可信提交或解释为可靠判定前必须处理；P2 表示在完整验收、持续使用和扩展工程前应处理。阶段性尚未实现的功能另外列出，不混同为代码缺陷。

## 2. 已确认的问题

### F01 · P1：提取器使用输入补写观测，未实际观测也能通过断言

位置：

- `src/cpp_assessor/judge/extractors.py:96`、`:105`：先复制 initial_contacts，再用 `stored_phone or phone` 补手机号，生日也来自输入。
- 同文件 `:174`、`:206`：生日提醒、检索的 contacts_after 直接返回输入中的初始通讯录。
- 同文件 `:199`：搜索结果按姓名匹配后直接复制初始联系人，覆盖实际打印的其他字段。

复现 R1：实际 stdout 只有 `4.[普通] 张三`，没有打印手机号、生日或真实编号。提取器却构造出编号 1、预期手机号和生日，T1 的 a_created、a_contacts 都为 MATCH。

复现 R2：实际输出没有“已有联系人”，提取器仍把输入中的该联系人写入 contacts_after，T1 非数字手机号用例的两条断言均为 MATCH。

复现 R3：stdout 中 Anna 的手机号明确为 `99999999999`，返回的 matches 却变成输入中的 `13800138000`。

影响：保存错误、原数据被清空、查询返回了错误字段等缺陷可能被掩盖。`observed_rows > 0` 不能证明所有字段都被观察到。

修正要求：

1. initial_contacts 只能作为初始化请求和比较依据，不能作为动作后实际状态。
2. 每个 actual 字段关联真实返回值、实际记录或原始输出位置。未观测的必需字段保持缺失并 NOT_COMPARED。
3. 观测前后状态分别采集；不能因为“查询理论上不改数据”就省略检查。
4. 不得按姓名字典合并不同记录，或按期望重编号、补电话；确需投影时由模板明确允许并保留证据。

验收：上述三个输入必须不能再让原断言全部 MATCH；输出明确错误的手机号须被保留为实际值。增加重复姓名、重复记录和操作后原数据消失的反例。

### F02 · P1：没有把基准判断程序和完整测试方法提供给 LLM，且限制了目标观测代码的生成

位置：`src/cpp_assessor/orchestrator/mode_two.py:395` 的 `_prompt_payload()`；`src/cpp_assessor/judge/extractors.py:1`；`src/cpp_assessor/planning/bundle.py:414` 附近的驱动/观测校验。

当前提示包含题意、Schema、断言部分字段、输入分区、用例输入、提取器描述及目标源码，但不包含：

- 基准判断程序 `task_library/shared/harness/test_entry.cpp` 的相关测试实现。
- 基准方法的完整 setup/action/observe/teardown 流程及字段映射示范。
- 基准方法为何选择这些观测、如何检查状态不变的证据链。

当前 stdin_script 路径要求模型从固定提取器中选择，不能为新的输出布局生成独立观测程序。函数驱动路径允许生成 C++，因此不是完全没有生成代码；但主要菜单路径的能力仍依赖人工维护正则和特定输出格式。

影响：目标输出格式一变，就需要开发者增加提取器；模式二容易退化为几份样例菜单的适配，而非用户要求的测试方法迁移。将“生成解析器”等同于“生成判据”的代码注释也与方案相反：观测代码可以针对目标生成，正确性标准应由可信断言固定。

修正要求：先准备并提供版本化的基准判断程序、公开正反例、完整方法和基准映射。模型输出目标驱动、必要的隔离内观测代码、断言绑定及迁移矩阵。宿主继续复算标准断言；输入输出转换不能代替测试方法迁移。

验收：使用一种从未在提取器注册表出现的菜单/记录输出布局，能够基于基准方法生成对应观测；不能靠新增一个写死该布局的宿主提取器才通过。

### F03 · P1：CHECKED 被当成充分验证，正式判定资格仅取决于后端

位置：`src/cpp_assessor/judge/aggregate.py:167`、`:187`、`:219`；`src/cpp_assessor/orchestrator/mode_two.py:1040`。

聚合只拦截 UNVERIFIED，CHECKED 可以产生 PASS 并在后端 attested 时给出 `grade_eligible=true`。模式二不进行目标判断程序的正反例校准，报告始终写 CHECKED。

复现 R4：CHECKED、其他条件成立、后端 attested 时，直接得到 PASS 和正式判定资格。

复现 R5：甚至在任务未发布、断言未确认、适配 UNVERIFIED 的情况下，只要某例标记学生崩溃，代码会在检查这些阻断条件之前返回 FAIL、grade_eligible=true。

影响：暂时因本地后端没有隔离而显示 false，并不表示资格计算正确。以后接上真实隔离后端，未验证的 AI 判断程序会自动进入正式判定。

修正要求：按方案区分观测、试测判定与正式判定。CHECKED 只能输出试测证据及 INCONCLUSIVE；CALIBRATED/REVIEWED 由与工件哈希关联的验证记录产生。崩溃/超限的学生责任分支不能绕过规则确认、适配资格和故障归因门禁。

验收：R4、R5 均不得 grade_eligible；未验证适配即使算出逐条 MATCH，也不能显示正式 PASS。模式一应使用已发布基准判断程序的有效校准记录，而非永久降级为 CHECKED。

### F04 · P1：迁移矩阵只检查分区名出现，显式覆盖缺口仍能通过

位置：`src/cpp_assessor/planning/bundle.py:449`；`src/cpp_assessor/orchestrator/mode_two.py:1060` 附近只保存缺口。

校验只对比分区 ID 集合，不检查每行 `status=covered`，也不检查 driver_step、observation、assertion_ids 与实际调用的对应关系。coverage_gaps 非空本身不阻止通过或进入报告聚合。

复现 R6：所有迁移行都为 gap、没有有效观测描述、另有“未执行必要步骤”的 coverage_gaps，仍 `validation.passed=true`。

复现 R9：function_driver 仅输出固定观测、不调用目标业务实现，静态校验也接受。静态检查无法普遍证明 C++ 语义正确，但当前后续又缺少调用证据审查和目标级校准，缺口没有被其他门禁接住。

修正要求：分别校验输入、操作、观测、断言的覆盖；检查引用和步骤存在；必需项 gap/ambiguous 阻断完整资格。加入基准方法到目标入口及生成代码位置的映射、审查与正反例校准。不能把模型声称 covered 当成已执行。

验收：R6 拒绝成为完整方案；固定输出、始终接受、始终拒绝、调用错函数的判断程序不得获得正式资格。

### F05 · P1：真实隔离后端未实现，观察型上传入口还自动绕过门禁

位置：`src/cpp_assessor/sandbox/local.py:56`；`src/cpp_assessor/selfcheck/runner.py:256`；Web `/reference` 路由 `src/cpp_assessor/interfaces/web/app.py:726`。

现有 local 后端明确为 HOST_PROCESS，network_block 和 filesystem_isolation 均为 false。它在教师宿主上启动编译器和提交程序，Job Object 限制资源不提供目标目录之外的文件访问隔离。

一般测评默认拒绝执行，这是已有保护；但 selfcheck 固定 `allow_unattested=True`，而 Web `/reference` 接受任意上传源码。即使服务器没有启用 `--allow-unattested-backend`，上传该页面仍会走本地真实执行。

影响：不评分、标记观察型或事后提示“不具备正式资格”，都不能阻止提交程序读写教师文件或访问网络。这违反任务书对不可信代码隔离的明确要求。

修正要求：接入符合要求的 Windows Sandbox/VM 后端；所有上传入口共享同一强制策略。若保留本地开发后端，默认只运行明确选定的可信开发样例，不对任意上传自动放行。

验收：默认配置下向 `/reference` 上传源码，不能在宿主启动它；网络与教师目录访问必须在隔离后端中实际受阻，不能只改变能力标志。

能力门禁另有独立复现 R8：`sandbox/gate.py:57` 只把 isolation=NONE 当缺少隔离，未强制检查 process_limit、clean_reset、filesystem_isolation。一个仅为 HOST_PROCESS 且上述三项为 false 的能力对象，只要其他已检查字段为 true，也能 attested=true。修复隔离后端时须同时补齐门禁，不能只把 network_block 标记改为 true。

### F06 · P1：LLM 构建参数和输出路径未经白名单/边界校验即执行

位置：`src/cpp_assessor/planning/bundle.py:89`、`:304`；`src/cpp_assessor/orchestrator/mode_two.py:596`、`:602`。

`compiler_flags` 是任意字符串数组，artifact_name 是任意字符串。validate_bundle 不校验两者。后者直接与运行目录拼接，绝对路径可逃出该目录；前者直接传给本地 g++。

复现 R7：带绝对输出路径以及插件加载选项的清单仍通过静态校验。本次只检查返回值，没有执行该参数或创建外部文件。

影响：模型或源码中的提示注入可以扩大本地构建权限。参数数组避免 shell 解释，但不阻止编译器自身支持的危险功能或输出路径越界。

修正要求：artifact_name 限定为固定安全文件名，最终路径解析后必须位于当前构建目录。编译选项使用注册工具链的正向白名单，拒绝插件、响应文件、工具链重定向、任意输出及搜索路径等。模型只选择受支持选项，不提交任意 argv。

验收：R7 必须被拒绝；路径和参数拒绝都发生在创建目录、写文件和编译之前。

### F07 · P1：生成驱动或基础设施编译失败被直接判为学生编译失败

位置：`src/cpp_assessor/orchestrator/mode_two.py:624`。

任何非 SUCCESS 编译结果都设置 SUBMISSION_COMPILE_ERROR，不检查 fault_owner，也不区分包含生成 driver.cpp 的构建。INFRA_ERROR、资源限额、模型写错函数签名、重复 main 等都进入该分支。

影响：学生原工程可能正常，模型生成代码却编译不过，最终得到学生 FAIL；此路径还绕过了适配修正循环，因为编译后没有 exe 就直接返回。

修正要求：先确定原提交构建契约，再分开构建原始程序与判断程序。只有已确认的原始源码编译错误可归责学生；生成物错误进入有界适配修正；缺环境归 INFRA_ERROR；无法区分为 BUILD_UNRESOLVED/UNKNOWN。

验收：用真实可编译的源码搭配有语法错误的生成驱动，应是适配失败或修正成功；模拟编译器缺失不应产生学生 FAIL。

### F08 · P2：实际构建忽略 LLM 声明的源文件、排除列表和 include 路径

位置：`src/cpp_assessor/orchestrator/mode_two.py:493`、`:507`、`:522`、`:542`。

target.sources、entry_files、excluded_files、include_dirs 有模型字段和部分存在性检查，但实际准备阶段复制全部源码，枚举所有 C++ 编译单元一起构建；排除规则反而来自基准工程。头文件目录也固定为生成目录。build.defines/libraries 记录到 BuildPlan，却没有作为参数完整传给编译器。

影响：带示例 main、测试 main、备用实现或嵌套 include 的工程，模型即使给了正确构建清单也可能链接失败。模型修正清单不会修复实际构建。非源码数据文件还会在准备阶段被丢弃。

修正要求：采用经过路径及工具链校验的目标构建集合；明确应用每个字段，未支持的字段必须拒绝，不能接受后忽略。目标数据文件按声明只读拷入隔离内初始化位置。

验收：工程包含 main.cpp、备用 demo.cpp 和 inc/ 头文件时，选择正确源文件后能避免重复 main 并找到头文件；改变 excluded_files 能真实改变构建。

### F09 · P2：LLM 运行与 CLI/Web 使用了不同数据库

位置：`src/cpp_assessor/orchestrator/mode_two.py:233` 写 `assessor.db`；`src/cpp_assessor/orchestrator/runner.py:261` 和 `src/cpp_assessor/interfaces/web/app.py:328` 使用 `app.sqlite3`。

影响：LLM 运行不会出现在 Web `/runs` 历史和标准入口的最近运行中，CLI status 查不到。直接结果页可读 JSON，所以一次演示未必发现；服务重启后没有报告的 LLM 运行无法从 Web 使用的数据库识别中断，可能一直显示等待。

修正要求：统一从配置/应用服务取得数据库；迁移旧文件中的 LLM 索引。LLM 事件也应进入同一 run_events，而不只写 events.jsonl。

验收：同一 LLM run_id 能由 CLI status、Web 历史、API 状态和结果页一致查询，重启后仍存在。

### F10 · P2：replay 不是冻结计划重放，模式二的观测路径也不匹配

位置：`src/cpp_assessor/interfaces/cli.py:257`、`:274`；模式二观测保存在 `src/cpp_assessor/orchestrator/mode_two.py:926` 附近。

命令只用旧观测重新计算断言，没有创建新运行、重编译或重执行；任务包哈希变化后只是警告并使用当前规则。它固定找 `evidence/cases/<case>/observation.json`，模式二却写 `evidence/observations/<case>.json`。

影响：模式二有效报告可能直接被 replay 说成“缺少观测”；模式一也不能验证同一冻结计划在相同环境是否真实复现。零断言重算还可能输出“replay 一致”。

修正要求：把旧证据重新判定另命名为 rejudge；replay 按原冻结计划创建新 run_id、记录父运行、校验环境及工件哈希并实际执行。哈希不符不能称为原计划重放。

验收：LLM 和标准模式的 replay 均产生新报告和新执行证据；原工件或环境变化时明确拒绝精确重放。

### F11 · P2：LLM 阶段不受总预算和取消检查覆盖

位置：`src/cpp_assessor/orchestrator/mode_two.py:834`、`:1186`；`src/cpp_assessor/llm/provider.py:139` 附近。

total_wall_ms 的截止时间直到正式 `_execute_cases()` 才开始，工程分析、多次 API 请求、生成修正、编译和探测不计入。取消只在正式用例循环检查，不会阻止之前的多轮请求与试跑；客户端还会对包括鉴权错误在内的 LLMError 重试。

影响：用户点击取消后，系统仍可继续请求模型、消耗费用和启动程序；设置的总限额不是整次运行限额。

修正要求：在 run 创建时设置全局 deadline 和调用计数；每次请求/编译/探测前后检查剩余预算，超时限制取局部与剩余总预算的较小值。鉴权和不支持参数等确定错误不重试。取消使后续阶段不再启动，并清理正在运行的进程。

验收：在 ANALYZING/PROBING 时取消不进入下一步；持续 API 超时会在全局预算内停止，不重新从正式执行阶段计时。

### F12 · P2：输出限额仅在结束后检查，且使用 max 而非 stdout+stderr 合计

位置：`src/cpp_assessor/sandbox/local.py:189`、`:202`；`src/cpp_assessor/sandbox/win32.py:327` 附近直接写文件并等待。

程序运行中可以持续写输出直到时间限制结束，事后才读取文件大小；合计 1 MiB 的设计被实现成两个流各自最大值限制。workdir_bytes 也没有对应的执行期磁盘配额实现。

影响：输出爆量先占满宿主磁盘，事后 OUTPUT_LIMIT 无法撤销影响；两个各低于上限但合计超限的输出不会被识别。

修正要求：在执行期间监控合计输出和工作目录用量，达到限额立刻终止整个任务进程树；在隔离外层设置真正磁盘配额。观测器与编译输出也有相应限制。

验收：持续写两路输出时，越过总量阈值即可终止，不必等墙钟耗尽；产生大数据文件也被配额阻止。

### F13 · P2：任务发布只检查静态结构，没有检查有效校准记录

位置：`src/cpp_assessor/tasks/loader.py:687`。

publish_task 调用静态 validate_task 后直接把 publication_status 写成 PUBLISHED，不要求当前包哈希对应的正确/缺陷版本真实校准成功。另有 tools/calibrate.py 并不等于发布路径使用了它的记录。

影响：结构正确但实际测试错误的自定义题可以被发布；修改后沿用旧的校准印象也不会被正式发布流程拒绝。

修正要求：静态检查和隔离校准分开记录；发布必须要求当前工件与环境对应的校准成功。已发布版本不可原地覆写，变更生成新版本。

验收：没有校准、校准失败、包哈希变化时不能发布；正确版本全部通过且缺陷由指定用例识别后才能发布。

### F14 · P2：模式一遇到不匹配工程会替换成单条观察型测试，掩盖原题覆盖缺口

位置：`src/cpp_assessor/orchestrator/runner.py:514`、`:1438`。

不匹配的提交会自动转 legacy 模式，不执行原题四至六例，而 `_legacy_coverage()` 只把自己的一条探针当计划，设置 complete=true，随后可能显示 PASS。报告备注虽说明不是完整评分，但主状态、原题 ID 和 coverage.complete 仍会让使用者误解。

影响：标准模式不再具有稳定契约；某个文件名能否匹配会改变测试范围，同一道题的“通过”含义不一致。未来后端通过门禁时，legacy 分支也缺少固定禁止正式资格的独立约束。

修正要求：标准模式不匹配就返回清晰的接口不符，建议用户改用 LLM 模式。若保留观察功能，单独建观察报告或明确的 exploratory 标记；保留原题未覆盖集合，不用缩小计划集合制造 complete。

验收：任意不匹配工程不能只测一条探针就获得原题 PASS；观察模式即使后端 attested 也不获得该题完整测评资格。
