# 实验报告（第一步：模式一 CLI 原型）

## 1. 实验目的

按《工程实践项目任务书》与《双模式测评系统架构与实施方案》v0.2 的第一步要求，
验证以下问题：

1. 以简化通讯录程序为对象，能否用**预配置用例 + 可信断言**稳定区分“正确实现”
   与“已知缺陷实现”；
2. 编译失败、运行时崩溃、超时、模拟执行等异常路径，能否被如实分类并给出
   可解释的判定，而不是误判为通过；
3. 判定结论能否与证据（请求、观测、原始输出、编译日志）一一对应并可复现；
4. 在隔离能力不足的本机环境中，系统能否**拒绝冒充正式评分**（能力门禁生效）。

## 2. 实验环境

| 项目 | 值 |
| --- | --- |
| 操作系统 | Windows 10/11 x64（工作区路径含中文） |
| Python | 3.12.10 |
| 依赖 | pydantic 2.14.1、jsonschema 4.26.0、pytest 9.1.1 |
| 编译器 | g++ 13.2.0（MinGW-W64 x86_64-ucrt-posix-seh，Brecht Sanders r8） |
| 执行后端 | `local_win32_job`（Windows Job Object）与 `mock` |
| 时间 | 2026-10-18 |

## 3. 实验方法

1. **题库构建**：编写简化通讯录基准工程（`task_library/projects/contactbook_base/1.0.0`），
   故意保留 5 处小缺陷；用 `tools/build_task_packages.py` 生成 5 个任务包，
   每包含初始工程、参考正确实现、缺陷实现、用例、断言与参照版本清单。
2. **静态校验**：`assessor task validate` 检查文件、Schema、引用、覆盖、哈希。
3. **校准**：`tools/calibrate.py` 对每题分别编译运行 `correct` 与 `faulty`，
   比对实际判定与期望判定，并要求缺陷实现的指定用例全部失败。
4. **异常场景**：构造学生提交（独立正确实现、仅交一个文件、语法错误、段错误、
   死循环、zip 提交、带修改前快照），走同一条 CLI 流程。
5. **自动化测试**：`python -m pytest` 运行单元与集成测试。
6. **证据复核**：`assessor replay <run_id>` 从证据重算断言。

## 4. 实验结果

### 4.1 任务包与用例

5 个任务包全部通过静态校验（每包 40 余项检查，含逐用例检查；T1 实测 51 项），共 26 个用例、10 条断言定义：

| 任务 | 用例数 | 断言 | 分区（含业务非法） |
| --- | --- | --- | --- |
| `t1_phone_validation` | 4 | `a_created`、`a_contacts` | 4（`non_digit_11`） |
| `t2_birthday_today` | 6 | `a_names`、`a_contacts` | 5（`negative_window`） |
| `t3_date_validation` | 6 | `a_created`、`a_contacts` | 6（5 个非法日期分区） |
| `t4_name_search` | 5 | `a_matches`、`a_contacts` | 5（`empty_keyword`） |
| `t5_id_allocation` | 5 | `a_id_list`、`a_contacts` | 5（`delete_nonexistent`） |

### 4.2 校准结果

命令：`python tools\calibrate.py`。判定标准：正确实现 `PASS` 且无失败用例；
缺陷实现得到声明判定且 `must_fail_cases` 全部失败。

| 任务 | 正确实现 | 缺陷实现 | 缺陷实现失败用例 |
| --- | --- | --- | --- |
| `t1_phone_validation` | PASS | FAIL | `c_non_digit_11` |
| `t2_birthday_today` | PASS | FAIL | `c_today_exact`、`c_today_window`、`c_leap_day` |
| `t3_date_validation` | PASS | FAIL | `c_invalid_1900_02_29`、`c_invalid_year_low`、`c_invalid_year_high` |
| `t4_name_search` | PASS | FAIL | `c_case_insensitive`、`c_upper_keyword` |
| `t5_id_allocation` | PASS | FAIL | `c_delete_then_add`、`c_max_seed`、`c_multi_add` |

5/5 题校准通过。注意：由于本机后端缺网络/文件系统隔离，
`grade_eligible` 恒为 `false`，校准只比较 `assessment_status` 与失败用例集合；
这是门禁设计的预期结果，不是校准失败。

### 4.3 异常与边界场景

| 场景 | 构造方式 | `execution_status` | 判定 | 关键表现 |
| --- | --- | --- | --- | --- |
| 正确实现 | `--variant correct` | `COMPLETED` | PASS | 4/4 用例一致，8 条断言一致 |
| 学生独立实现（循环 + `isdigit`） | 目录提交 | `COMPLETED` | PASS | 未按参考补丁逐字复制也能通过 |
| 只提交 `validators.cpp` | 单文件 | `COMPLETED` | PASS | 相对路径覆盖生效 |
| zip 提交 + `--target-before` | 压缩包 + 基准快照 | `COMPLETED` | PASS | 两个快照均入清单 |
| 语法错误 | 删右括号 | `SUBMISSION_COMPILE_ERROR` | FAIL | 0 个用例执行，`evidence/compile/stderr.txt` 可查 |
| 运行时崩溃 | `std::raise(SIGSEGV)` | `COMPLETED` | FAIL | 4 例 `CRASH`/`SUBJECT_FAULT`，判 `SUBJECT_CRASH_OR_LIMIT` |
| 死循环 | `while (true) {}` | `COMPLETED` | FAIL | 4 例 `WALL_TIME_LIMIT`，约 12 s 后全部终止 |
| 模拟后端 | `--backend mock` | `COMPLETED` | PASS | 报告注明“未运行任何被测代码”，`sandbox_attested=false` |
| 未过门禁且未放行 | 不加 `--allow-unattested-backend` | `UNSUPPORTED` | NOT_ASSESSED | 拒绝执行，提示放行参数 |
| 证据复现 | `assessor replay` | — | — | 4 用例、8 断言逐条一致 |

崩溃场景有一个值得记录的细节：最初用 `*nullptr = 1` 制造崩溃，`-O2` 下属于
未定义行为，写入被优化掉，程序反而正常返回，结果退化成“缺陷实现”。改用
`std::raise(SIGSEGV)` 后才稳定触发 `CRASH`。这说明**故障注入必须可观测**，
不能依赖编译器“碰巧”保留未定义行为。

## 5. 结果分析

1. **缺陷与用例一一对应**：每个缺陷至少被一个“正常或边界”用例击中。
   例如 T1 的 `c_non_digit_11` 用 `1380013800a` 同时满足长度 11、首位 1，
   只差“后 10 位必须是数字”，因此能精确定位缺陷；T2 的 `c_today_exact`
   把“当天生日”从“已过去”中分离出来；T5 的 `c_delete_then_add` 覆盖
   “删除后复用 size+1”导致编号重复的路径。
2. **判定没有被“缺观测”稀释**：学生崩溃/超时虽然导致用例未比较、覆盖不完整，
   但聚合器把学生侧故障置于覆盖阻塞项之前，稳定判 `FAIL`。这修正了早期版本
   会把崩溃误判为 `INCONCLUSIVE` 的问题。
3. **适配器故障与学生故障分离**：观测缺失、非法 JSON、ID 不匹配分别归因
   `SUBMISSION`/`UNKNOWN`/`ADAPTER`，避免“驱动 bug 算学生错”。
4. **门禁确实阻止了“假正式评分”**：本机所有报告 `grade_eligible=false`，
   原因明确写为 `EXECUTION_BACKEND_NOT_ATTESTED`；模拟后端另有专门说明。

## 6. 开发中发现并修复的问题

| 问题 | 现象 | 修复 |
| --- | --- | --- |
| 快照根路径用错 | 提交覆盖时 `FileNotFoundError: README.md` | `ingest` 的文件在 `root/original` 下，合成与构建均改用该目录 |
| 执行状态被覆盖 | 编译失败仍显示 `COMPLETED` | 增加 `execution_status_decided` 标志，阶段内已定状态不被收尾覆盖 |
| 崩溃场景未触发 | `*nullptr=1` 被 `-O2` 优化掉 | 夹具改用 `std::raise(SIGSEGV)` |
| 崩溃被判 INCONCLUSIVE | 覆盖缺口阻塞项先于学生故障 | 聚合器把学生侧崩溃/超限提前判定为 `FAIL` |
| 枚举值不一致 | `CompileStatus.FAILED`、`ValidationLevel.FULL` 不存在 | 改用 `COMPILER_ERROR`、`CHECKED/UNVERIFIED` |
| CSV 中文乱码 | Excel 打开乱码 | 导出改为 UTF-8 BOM；控制台管道统一 UTF-8 |
| 必需断言未比较仍可能 PASS | 观测缺字段时聚合只看 MISMATCH | 增加 `ASSERTIONS_NOT_COMPARED` 阻塞项 |

## 7. 结论

- 第一步目标达成：5 道小改题可在 CLI 下一次命令完成“编译—执行—比对—报告”，
  正确实现全部通过、缺陷实现全部被指定用例识别，且有证据可复现。
- 异常路径（编译失败、崩溃、超时、模拟执行、门禁拒绝）均有明确、可解释、
  可区分的状态与判定，满足任务书“验证正确实现通过、缺陷实现被识别”的要求。
- 系统没有把“没测到”当成“通过”，也没有把“未过门禁”包装成正式成绩；
  这两点是后续接入 LLM 与 Web 之前必须保持的底线。

## 8. 局限与下一步

1. 本机后端不具备网络与文件系统隔离，正式评分需接入 Windows Sandbox 或固定 VM；
2. 题库需从 5 题扩展到 10 题、用例从 26 个扩展到 ≥40 个；
3. 尚未实现 LLM 诊断（任务 3）、模式二与 Web 界面（任务 4）；
4. 需补充“函数级驱动”和更多“操作前后不变”的用例；
5. 需在正式后端上重跑全套校准，并把结果写回任务版本的 `validation_level`。
