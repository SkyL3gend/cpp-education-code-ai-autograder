# 实验报告（第一步：模式一 CLI + 本地 Web 原型）

## 1. 实验目的

按《工程实践项目任务书》与《双模式测评系统架构与实施方案》v0.2 的第一步要求，
验证以下问题：

1. 以简化通讯录程序为对象，能否用**预配置用例 + 可信断言**稳定区分“正确实现”
   与“已知缺陷实现”；
2. 编译失败、运行时崩溃、超时、模拟执行等异常路径，能否被如实分类并给出
   可解释的判定，而不是误判为通过；
3. 判定结论能否与证据（请求、观测、原始输出、编译日志）一一对应并可复现；
4. 在隔离能力不足的本机环境中，系统能否**拒绝冒充正式评分**（能力门禁生效）。

## 3. 实验方法

1. **题库构建**：编写简化通讯录基准工程（`task_library/projects/contactbook_base/1.0.0`），
   故意保留 5 处小缺陷；用 `tools/build_task_packages.py` 生成 5 个任务包，
   每包含初始工程、参考正确实现、缺陷实现、用例、断言与参照版本清单。
2. **静态校验**：`assessor task validate` 检查文件、Schema、引用、覆盖、哈希。
3. **校准**：`tools/calibrate.py` 对每题分别编译运行 `correct` 与 `faulty`，
   比对实际判定与期望判定，并要求缺陷实现的指定用例全部失败。
4. **异常场景**：构造学生提交（独立正确实现、仅交一个文件、语法错误、段错误、
   死循环、zip 提交、带修改前快照），走同一条 CLI 流程。
5. **自动化测试**：`python -m pytest` 运行单元与集成测试。
6. **证据复核**：`assessor replay <run_id>` 从证据重算断言。

### 4.2 校准结果

命令：`python tools\calibrate.py`。判定标准：正确实现 `PASS` 且无失败用例；
缺陷实现得到声明判定且 `must_fail_cases` 全部失败。

| 任务 | 正确实现 | 缺陷实现 | 缺陷实现失败用例 |
| --- | --- | --- | --- |
| `t1_phone_validation` | PASS | FAIL | `c_non_digit_11` |
| `t2_birthday_today` | PASS | FAIL | `c_today_exact`、`c_today_window`、`c_leap_day` |
| `t3_date_validation` | PASS | FAIL | `c_invalid_1900_02_29`、`c_invalid_year_low`、`c_invalid_year_high` |
| `t4_name_search` | PASS | FAIL | `c_case_insensitive`、`c_upper_keyword` |
| `t5_id_allocation` | PASS | FAIL | `c_delete_then_add`、`c_max_seed`、`c_multi_add` |

5/5 题校准通过。注意：由于本机后端缺网络/文件系统隔离，
`grade_eligible` 恒为 `false`，校准只比较 `assessment_status` 与失败用例集合；
这是门禁设计的预期结果，不是校准失败。

### 4.3 异常与边界场景

| 场景 | 构造方式 | `execution_status` | 判定 | 关键表现 |
| --- | --- | --- | --- | --- |
| 正确实现 | `--variant correct` | `COMPLETED` | PASS | 4/4 用例一致，8 条断言一致 |
| 学生独立实现（循环 + `isdigit`） | 目录提交 | `COMPLETED` | PASS | 未按参考补丁逐字复制也能通过 |
| 只提交 `validators.cpp` | 单文件 | `COMPLETED` | PASS | 相对路径覆盖生效 |
| zip 提交 + `--target-before` | 压缩包 + 基准快照 | `COMPLETED` | PASS | 两个快照均入清单 |
| 语法错误 | 删右括号 | `SUBMISSION_COMPILE_ERROR` | FAIL | 0 个用例执行，`evidence/compile/stderr.txt` 可查 |
| 运行时崩溃 | `std::raise(SIGSEGV)` | `COMPLETED` | FAIL | 4 例 `CRASH`/`SUBJECT_FAULT`，判 `SUBJECT_CRASH_OR_LIMIT` |
| 死循环 | `while (true) {}` | `COMPLETED` | FAIL | 4 例 `WALL_TIME_LIMIT`，约 12 s 后全部终止 |
| 模拟后端 | `--backend mock` | `COMPLETED` | PASS | 报告注明“未运行任何被测代码”，`sandbox_attested=false` |
| 未过门禁且未放行 | 不加 `--allow-unattested-backend` | `UNSUPPORTED` | NOT_ASSESSED | 拒绝执行，提示放行参数 |
| 证据复现 | `assessor replay` | — | — | 4 用例、8 断言逐条一致 |

崩溃场景有一个值得记录的细节：最初用 `*nullptr = 1` 制造崩溃，`-O2` 下属于
未定义行为，写入被优化掉，程序反而正常返回，结果退化成“缺陷实现”。改用
`std::raise(SIGSEGV)` 后才稳定触发 `CRASH`。这说明**故障注入必须可观测**，
不能依赖编译器“碰巧”保留未定义行为。

### 4.6 基准程序实测（观察型）

用 `python assessor.py selfcheck` 对《参考基准程序/通讯录_v6最终版.cpp》真实编译、
脚本化驱动 5 条检查，结果如下（`sandbox_attested=false`，因本机后端缺网络/文件系统
隔离；实测不评分，允许在该后端下运行）：

| 检查 | 驱动方式 | 观察到的行为 | 结论 |
| --- | --- | --- | --- |
| `smoke_menu` | 输入容量、`0` 退出 | 打印主菜单并正常退出 | `PASS` |
| `phone_digits` | 添加联系人，手机号先输 `1380013800a` 再输合法号 | 缺陷版直接接受 `1380013800a` 并入库 | `DEFECT` |
| `birthday_today` | 生日提醒，今天 `2026-10-08`、`days_ahead=0` | 当天生日的“测试联系人2”出现在结果中 | `PASS` |
| `name_search_case` | 添加 `Anna`、`annabel`，搜索 `an` | 只返回 `annabel`，大小写敏感 | `DEFECT` |
| `date_validation` | 输入 `1900 2 29`、`2023 4 31`，再输合法日期 | 两次均拒绝并提示，合法日期被接受 | `PASS` |

两条 `DEFECT` 与五题题库里 T1、T4 的已知缺陷同源，可互相印证；`PASS` 表示
“脚本驱动到位且行为符合规则”，不代表程序整体正确。五条检查各自的 `stdin.txt`、
`stdout.txt`、`stderr.txt` 都保存在 `data/selfchecks/<selfcheck_id>/cases/`，
可与结论逐条对照。

这说明：除了五题使用的 `test_entry.cpp` 请求/观测协议，系统还能直接驱动真实
菜单式程序（标准输入脚本 + 原始输出提取），不是只会运行自己写的驱动。

批量链路第一次联调时出现过“批次永远停在 running”：轮询读取 `batch.json` 的同一
瞬间，工作线程用 `os.replace` 做原子替换，在 Windows 上抛出 `PermissionError`

list-of-tuples 提交 multipart 会得到 422，改为 `data={"tasks": [...]}` 即正常，
服务端本身没有问题。

同一轮还验证了三条边界：

1. **缺 Key**：`assessor run --llm` 未配置 Key 时直接报

线上又以真实 Key 走通一次 `POST /llm/runs`（就是上表的 `FAIL` 运行）。

- **函数驱动**：把基准工程去掉 `main_menu.cpp` 后提交（`data/tmp/mt/base_nomian`），
  模型选择 `function_driver`，编译 `generated/driver/driver.cpp` 并链接 `contactbook.cpp`
  （`run_20261019_021237_538b43`）。4 个用例 3 个 `MATCH`，`c_non_digit_11`
  `MISMATCH`（基准工程本身是带缺陷的起点版本，接受非数字号码）→ `FAIL`。
- **菜单驱动**：直接提交带菜单的基准工程（`run_20261019_021107_46c837`）→ `PASS`，
  证明 `stdin_script` + 列表/搜索提取对第二种菜单格式同样可用。

为支持这些题，适配层补了三件事：`driver.seed_session`（按用例 `initial_contacts`
预建联系人，宿主对每个联系人重复执行并接在正式剧本前）、`driver.session_by_case`
（按用例覆盖剧本）、提取器同时识别 `4.[普通] 张三` 与 `#4 张三  手机:…` 两种列表行。

已知边界：菜单程序无法把联系人编号改成用例声明的任意值，因此 T5 这类“初始编号不连续”
的题只能得到 `INCONCLUSIVE`；模型生成的剧本仍可能错位，宿主用探针试跑 + 两轮有界修正兜底。

## 5. 结果分析

1. **缺陷与用例一一对应**：每个缺陷至少被一个“正常或边界”用例击中。
   例如 T1 的 `c_non_digit_11` 用 `1380013800a` 同时满足长度 11、首位 1，
   只差“后 10 位必须是数字”，因此能精确定位缺陷；T2 的 `c_today_exact`
   把“当天生日”从“已过去”中分离出来；T5 的 `c_delete_then_add` 覆盖
   “删除后复用 size+1”导致编号重复的路径。
2. **判定没有被“缺观测”稀释**：学生崩溃/超时虽然导致用例未比较、覆盖不完整，
   但聚合器把学生侧故障置于覆盖阻塞项之前，稳定判 `FAIL`。这修正了早期版本
   会把崩溃误判为 `INCONCLUSIVE` 的问题。
3. **适配器故障与学生故障分离**：观测缺失、非法 JSON、ID 不匹配分别归因
   `SUBMISSION`/`UNKNOWN`/`ADAPTER`，避免“驱动 bug 算学生错”。
4. **门禁确实阻止了“假正式评分”**：本机所有报告 `grade_eligible=false`，
   原因明确写为 `EXECUTION_BACKEND_NOT_ATTESTED`；模拟后端另有专门说明。
5. **Web 端没有引入第二套判定**：Web 与 CLI 的结论、证据、计数完全来自同一份
   `objective_report.json`，因此 `replay` 与导出行为一致；Web 只增加了上传、
   异步等待与页面渲染。

## 6. 开发中发现并修复的问题

| 问题 | 现象 | 修复 |
| --- | --- | --- |
| 快照根路径用错 | 提交覆盖时 `FileNotFoundError: README.md` | `ingest` 的文件在 `root/original` 下，合成与构建均改用该目录 |
| 执行状态被覆盖 | 编译失败仍显示 `COMPLETED` | 增加 `execution_status_decided` 标志，阶段内已定状态不被收尾覆盖 |
| 崩溃场景未触发 | `*nullptr=1` 被 `-O2` 优化掉 | 夹具改用 `std::raise(SIGSEGV)` |
| 崩溃被判 INCONCLUSIVE | 覆盖缺口阻塞项先于学生故障 | 聚合器把学生侧崩溃/超限提前判定为 `FAIL` |
| 枚举值不一致 | `CompileStatus.FAILED`、`ValidationLevel.FULL` 不存在 | 改用 `COMPILER_ERROR`、`CHECKED/UNVERIFIED` |
| CSV 中文乱码 | Excel 打开乱码 | 导出改为 UTF-8 BOM；控制台管道统一 UTF-8 |
| 必需断言未比较仍可能 PASS | 观测缺字段时聚合只看 MISMATCH | 增加 `ASSERTIONS_NOT_COMPARED` 阻塞项 |
| Web 报告页报模板错 | Jinja 无 `extract` 过滤器 | 注册 `reason_label` 过滤器 |
| Web 轮询读到半状态 | 报告已落盘、SQLite 尚未收尾 | 状态接口以报告文件为准补充字段 |
| Web 测试用错后端 | mock 按 expected 合成观测，缺陷版也 PASS | 缺陷版用例改用真实 g++ 后端 |
| 非法提交把运行卡死 | 提交无关源码后运行停在 `REPORTING`，页面 404：异常类的 `execution_status` 是字符串，`_finish()` 调 `.value` 抛 `AttributeError`；随后 `_assemble_report` 又要求 plan 非空 | 异常状态改为 `ExecutionStatus` 枚举并在收尾归一；报告允许 `plan/build_plan/validation` 缺失（覆盖按未执行统计）；失败仍落盘 `INVALID_INPUT`/`NOT_ASSESSED` 报告 |
| 提交后立即 404 | 303 重定向早于后台线程建库/建目录 | 运行页把“已排队/目录已存在”视为等待页；补充运行中断检测与 400 路径校验 |
| 误把参考资料当提交 | 提交《参考基准程序/通讯录_v6最终版.cpp》被拒（早期版本 `INVALID_INPUT`） | 任务页给出“下载可修改工程”（`base.zip`）与说明；v0.4.1 起不再拒绝，改为单文件适配（观察型）并明确标注不是完整评分 |
| 批量只收 ZIP | 学生交单个 `.cpp` 或带依赖的工程时无法批量 | 每个上传物落成 `programs/<id>/` 独立文件夹（`source/` + `verifier/`），ZIP 解压带路径校验，多文件统一编译后走观察型适配 |
| 多文件程序编译失败 | 只取最大 `.cpp`，`#include "contactbook.h"` 找不到 | ZIP 解压进同一目录后把全部 `.cpp` 一起编译，`include_dirs` 指向该目录 |
| 批量批次永远 running | `batch.json` 原子替换时被页面读取，Windows 抛 `PermissionError`，工作线程死亡 | 替换加有限重试；执行循环包 `try/finally`，批次级异常把未完成格标为 `failed` 并写原因 |
| 批量测试 422 | `TestClient` 以 list-of-tuples 发 multipart，字段丢失 | 测试改为 `data={"tasks": [...]}`；服务端加表单字段校验与 400 说明 |
| 模式二首轮失败崩溃 | 模型首次回复解析失败后 `state.validation` 仍为 `None`，收尾时访问 `.problems` 抛 `AttributeError` | 记录最后一轮错误并落失败报告；`None` 时按“清单未通过”收尾 |
| 模型枚举大小写不一致 | 返回 `STDIN_SCRIPT`、`TRUSTED_EXTRACTOR`、`BOUND`、`MAPPED` 等大写值 | 模型层做大小写归一；校验失败时把“允许的取值”写进回喂的问题列表 |
| 生日观测为空 | `observer.params["birthday"]` 被替换成 Python `repr(dict)`，提取器解析失败 | 整串占位符保留原值（dict 原样传入），参数也可拆成 `birthday.year/month/day` |
| 菜单程序提前返回导致脚本错位 | 非法手机号时程序立刻回添加菜单，后续“生日/城市/地址”被当成菜单选择，无限循环直到超时 | 支持 `session_by_case` 逐用例会话；提示词要求“每步只喂一个输入、不要依赖返回层数” |

## 7. 结论

- 第一步目标达成：5 道小改题可在 CLI 下一次命令完成“编译—执行—比对—报告”，
  正确实现全部通过、缺陷实现全部被指定用例识别，且有证据可复现。
- 新增的本地 Web 界面复用同一套运行器与判定：浏览器里可选任务、上传提交、
  等待结果、下载 JSON/CSV，结论与 CLI 完全一致。
- 新增的基准程序实测用同一套隔离与工件设施，直接驱动真实菜单程序，
  用五条检查复现了参考程序自身的两处行为缺陷（手机号、大小写检索），
  且明确与评分链路分离。
- 异常路径（编译失败、崩溃、超时、模拟执行、门禁拒绝）均有明确、可解释、
  可区分的状态与判定，满足任务书“验证正确实现通过、缺陷实现被识别”的要求。
- v0.4.0 的界面改进（模式选择、中英双语、批量矩阵）都只作用于展示与调度层：
  同一次运行的 `objective_report.json`、证据与 `replay` 结果不因语言或批量入口改变。
- v0.4.1 起，完整程序（单文件或带依赖的多文件 ZIP）可以直接放进五道题测评：
  运行器不再拒绝，而是把全部源文件编译后按题目的菜单脚本做一次“观察型适配”，
  报告给出 `single_file_*` 用例与明确说明。它只核对一条可观察规则、不跑任务包声明的
  断言用例，因此**是参考信息，不是完整评分**——这条边界在报告、页面与文档中一致。
- 系统没有把“没测到”当成“通过”，也没有把“未过门禁”包装成正式成绩；
  这两点是后续接入 LLM 与完整 Web 功能之前必须保持的底线。
- v0.5.0 的模式二把“怎么测一份陌生程序”交给模型生成声明式清单，再由宿主的
  静态校验、协议校验与试跑把关；判定仍由断言引擎完成。真实模型在 T1 上复现了
  预期的两个结论（原版 `FAIL`、修复版 `PASS`），说明“模型只适配、不判分”的
  分工可行，且报告可解释、可复现。
- 模式二对“适配失败”与“学生程序错误”做了明确分离：前者记
  `ADAPTATION_FAILED`/`INCONCLUSIVE`，后者才可能 `FAIL`；这条边界是 LLM 参与
  测评时最容易被混淆、也最需要守住的地方。

## 8. 局限与下一步

1. 本机后端不具备网络与文件系统隔离，正式评分需接入 Windows Sandbox 或固定 VM；
2. 题库需从 5 题扩展到 10 题、用例从 26 个扩展到 ≥40 个；
3. 尚未实现 LLM 诊断（任务 3：错误定位与修复建议）；模式二已实现并跑通 T1，
   Web 端仍无登录、鉴权、班级与成绩管理；
4. 批量测评串行执行（上限 10 程序 × 5 题），页面轮询间隔 2 s，暂不面向大规模班级；
5. 需补充“函数级驱动”和更多“操作前后不变”的用例；
6. 需在正式后端上重跑全套校准，并把结果写回任务版本的 `validation_level`；
7. 基准程序实测固定为 5 条检查、依赖原程序菜单文本作为锚点，换程序时需要
   调整检查定义，驱动不到的位置只报 `NOT_OBSERVED`。
8. 单文件适配（观察型）每题只核对一条可观察规则，且依赖菜单文本锚点；
   换一份界面完全不同的程序时可能只得到 `INCONCLUSIVE`。要完整评分仍需按接口
   提交（`validators.cpp` / `contactbook.h` 等），或为题目增加函数级驱动。
9. 批量测评中每个程序的 `verifier/` 目录已经预留，但“按程序生成不同判定代码”
   尚未实现，目前所有程序共用题目自带的判定规则。
10. 模式二只做“客观测评”的适配，不做 LLM 诊断；清单生成依赖模型的稳定性，
    当前仅 T1 用真实模型校准，T2—T5 需要逐题验证。模型失效或程序不可读时
    只能给出 `ADAPTATION_FAILED`/`UNSUPPORTED`，不会降级成“通过”。
11. 模式二的 `function_driver` 已实现但缺少真实题目样例；现阶段真实模型主要
    生成 `stdin_script` 会话，菜单结构变化时仍需人工检查清单。
