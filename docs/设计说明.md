# 设计说明

本文说明原型的分层结构、数据契约、执行协议与判定规则，并明确它与
《双模式测评系统架构与实施方案》v0.2 的对应关系及本期简化点。
目标不是复述方案，而是让后续开发者知道**代码在哪里、契约是什么、哪些还没做**。

---

## 1. 范围与设计原则

- 本期交付：**模式一（标准测评）** 的完整闭环，CLI 界面，5 道小改题。
- 三条硬约束贯穿实现：
  1. **正确性由预配置用例与可信断言判定**，LLM 不参与判分（本期未接入 LLM）；
  2. **被测代码不在宿主直接运行**，没有“后端不可用就本地直跑”的兜底路径；
  3. **“没测到”绝不等于“通过”**：覆盖缺口、观测缺失、适配器故障一律
     `INCONCLUSIVE` 或 `NOT_ASSESSED`，只有全部必需断言一致才 `PASS`。
- 模块依赖方向：`interfaces → orchestrator → {intake, tasks, sandbox, judge, storage, reporting} → domain`。
  `domain` 不依赖任何运行期组件；`judge` 不调用沙箱、不读数据库、不调 LLM。

## 2. 模块职责

| 包 | 职责 | 关键文件 |
| --- | --- | --- |
| `domain` | 枚举、pydantic 数据模型、JSON Pointer、规范化、错误类型、canonical JSON/hash | `enums.py`、`models.py`、`pointers.py`、`errors.py`、`canonical.py` |
| `intake` | 目录/单文件/zip 导入、路径策略、编码识别、只读快照与清单 | `snapshot.py`、`path_policy.py` |
| `tasks` | 任务包加载、静态校验、发布、提交与基准工程合成、源文件枚举 | `loader.py` |
| `sandbox` | 后端接口、能力门禁、Win32 Job Object 后端、模拟后端 | `base.py`、`gate.py`、`win32.py`、`local.py`、`mock.py` |
| `orchestrator` | 请求信封/观测解析、标准测评运行器（状态机、预算、取消、证据落盘） | `protocol.py`、`runner.py` |
| `judge` | 规范化、断言白名单、覆盖计算、判定聚合 | `normalizations.py`、`assertions.py`、`coverage.py`、`aggregate.py` |
| `storage` | SQLite 运行/事件/工件/校准记录；运行目录工件存储 | `db.py`、`artifacts.py` |
| `reporting` | JSON/CSV 导出、控制台摘要 | `export.py` |
| `interfaces` | CLI 命令与退出码 | `cli.py` |

`config.py` 负责路径解析（`ASSESSOR_HOME`、`ASSESSOR_TASK_LIBRARY`）、
工具链标识与版本常量；所有路径都从仓库根推导，不依赖当前工作目录。

## 3. 执行流程与状态机

模式一固定路径（编译发生在 `EXECUTING` 内）：

```
CREATED → INGESTING → RESOLVING_TASK → VALIDATING → FROZEN
        → EXECUTING → REPORTING → COMPLETED
```

| 阶段 | 动作 | 失败时 |
| --- | --- | --- |
| `INGESTING` | 导入提交/参照版本/`target_before`，写只读快照与清单 | `INVALID_INPUT` |
| `RESOLVING_TASK` | 加载任务包、校验哈希与发布状态 | 任务包错误 → `INFRA_ERROR`；草稿未放行 → `INVALID_INPUT` |
| `VALIDATING` | 合成工程、写构建计划、九项检查、能力门禁 | 门禁拒绝 → `UNSUPPORTED`（`NOT_ASSESSED`） |
| `FROZEN` | 固定 `test_plan.json` 与 `validation.json` | — |
| `EXECUTING` | 编译 → 逐用例执行 → 解析观测 → 断言比较 | 编译失败 → `SUBMISSION_COMPILE_ERROR`；总墙钟超限 → `BUDGET_EXCEEDED` |
| `REPORTING` | 计算覆盖与判定、写 `objective_report.json`、更新 SQLite | 内部异常 → `FAILED` |
| `COMPLETED` | 正常结束（包括预期内的失败结论） | — |

取消通过运行目录下的 `CANCEL` 文件实现，在阶段边界与用例之间检查；
取消是协作式的，最坏要等当前用例达到墙钟上限。

## 4. 提交导入

- 支持目录、单文件、zip。zip **不使用 `extractall`**：先校验成员路径，拒绝
  绝对路径、`..`、盘符、UNC、ADS、设备名、符号链接、大小写折叠重复，再逐块
  读取并累计大小/文件数，最后落盘。
- 上限：压缩包 20 MiB、解压总量 100 MiB、单文件 8 MiB、文件数 500。
- 编码识别顺序：UTF-8 → GBK → 二进制；清单记录每个文件的大小、sha256、编码。
- 快照目录只读使用，运行期不会修改提交原件。
- 合成规则：按相对路径覆盖基准工程 → 基本名唯一时覆盖 → 作为新文件加入；
  提交必须包含源码/头文件且至少匹配一个基准源码文件，避免“空提交通过”。

## 5. 任务包

必需文件：`task.json`、`io_template.json`、`test_method.json`、`cases.json`、
`reference_suite.json`、`reference_verifier/assertions.json`。

- `TaskSpec`：任务 ID/版本、标题、说明、规则（`rule_id + statement`）、用例 ID 列表、
  三个内容引用（IO 模板、测试方法、已验判断程序）、发布状态、oracle 来源。
- `IOTemplate`：`operation_id`、输入/输出 JSON Schema（2020-12、根对象、
  `additionalProperties: false`、禁止远程 `$ref`）、字段语义、前置条件、
  动作前观测（`pre_operations`）、必需观测键、允许变换、编码、退出契约、能力需求。
- `TestMethodSpec`：主题层级、规则引用、输入分区（含 `business_invalid`）、
  边界要求、步骤、观测、断言、覆盖要求、已验判断程序引用、已知缺陷矩阵。
- `TaskCase`：输入、期望（用于 `CASE_EXPECTED` 指针）、分区、断言、目的、
  限制覆盖、oracle 状态（`CONFIRMED`）。
- `ReferenceSuite`：恰好一个 `CORRECT`（期望 `PASS`）+ 至少一个 `FAULTY`
  （期望 `FAIL`/`INCONCLUSIVE`），每个变体声明覆盖文件与必须失败的用例。

校验器逐项检查并记录 `ValidationCheck`，任一项失败即拒绝加载/发布；
任务包哈希覆盖任务目录、基准工程目录与共享测试驱动目录。

## 6. 测试协议

### 6.1 请求

```json
{
  "protocol_version": "1.0",
  "run_id": "...", "attempt_id": "...", "case_id": "...",
  "operation_id": "create_contact",
  "input": { "...": "用例输入" }
}
```

**不含 `expected` 或任何答案字段**。请求文件保存在 `plans/requests/<case>.json`，
既作为 stdin，也用于事后复核。

### 6.2 观测

被测程序向 stdout 输出**最后一行** JSON：

```json
{
  "protocol_version": "1.0",
  "run_id": "...", "attempt_id": "...", "case_id": "...", "operation_id": "...",
  "status": "OK",
  "actual": { "created": true, "contacts_after": [] }
}
```

`status` 取值：`OK`、`INVALID`、`OBSERVATION_UNAVAILABLE`、`ADAPTER_ERROR`。
协议中**没有 PASS/FAIL**；观测只描述事实。

### 6.3 解析与归因

| 情况 | `protocol_status` | 归因 | 结论影响 |
| --- | --- | --- | --- |
| 正常 `OK` 且 `actual` 为对象，ID 全部匹配 | `OK` | `NONE` | 进入断言比较 |
| 崩溃/超时/超限，无输出 | `MISSING` | `SUBMISSION` | `FAIL`（`SUBJECT_CRASH_OR_LIMIT`） |
| 正常退出但没有输出 | `MISSING` | `SUBMISSION` | 未比较 |
| 最后一行不是合法 JSON | `MISSING` | `UNKNOWN` | `INCONCLUSIVE` |
| 协议版本/ID 不匹配、`OK` 无对象 `actual`、未知状态 | `INVALID` | `ADAPTER` | `INCONCLUSIVE` |
| `INVALID` / `ADAPTER_ERROR` | `INVALID` | `ADAPTER` | `INCONCLUSIVE` |
| `OBSERVATION_UNAVAILABLE`（业务调用抛异常） | `MISSING` | `SUBMISSION` | 未比较，结合覆盖判 `FAIL`/`INCONCLUSIVE` |

`OK` 的观测还会按 `output_schema` 校验；不符合则改判 `INVALID`、归因 `ADAPTER`，
防止“驱动输出形状错了却拿学生开刀”。

## 7. 判定引擎

### 7.1 断言

只有三种算子，均为白名单：

| 算子 | 语义 |
| --- | --- |
| `EQUALS` | 严格相等：区分 `bool`/`number`/`string`/`null`，`True` 不等于 `1`；对象递归比较；`int` 与 `float` 按数值相等 |
| `MULTISET_EQUALS` | 两侧必须是数组，按多重集合比较：顺序无关，**重复项仍计数** |
| `UNCHANGED` | 必须来自动作前观测（`PRE_OBSERVATION`），比较前后是否一致 |

期望来源两种：`CASE_EXPECTED`（用例 `expected` 中的 JSON Pointer）与
`PRE_OBSERVATION`（动作前观测的键 + 指针）。指针严格按 RFC 6901 解析，
缺失字段返回 `NOT_COMPARED` 并记录中文原因，绝不当成“相等”。

规范化首批只有 `identity_v1` 与 `lf_text_v1`（换行统一为 `\n`）。

### 7.2 覆盖

`compute_coverage` 以“已执行到产生结果”的用例为完成（**崩溃/超限也算完成**，
否则学生崩溃会被误判成“任务包问题”），计算：

- 必测用例 vs 完成用例；
- 必测分区 vs 完成用例覆盖的分区；
- 必测断言 vs 实际执行过的断言；
- `complete` 要求三者均无缺口。

### 7.3 聚合优先级

```
1. CANCELLED / INVALID_INPUT / UNSUPPORTED        → NOT_ASSESSED
2. SUBMISSION_COMPILE_ERROR                       → FAIL（不跑用例）
3. 其它非 COMPLETED 的执行状态                     → INCONCLUSIVE
4. 无用例结果                                      → NOT_ASSESSED
5. 出现学生侧崩溃/超限（termination ∈ 限制集合，
   note 不属于 ADAPTER/INFRA，或 note=SUBJECT_FAULT）→ FAIL
6. 规则未发布 / 断言未确认 / 校验未验证 / 覆盖不全 /
   适配器或基础设施故障 / 必需断言未比较            → INCONCLUSIVE
7. 任一必需断言 MISMATCH                           → FAIL
8. 全部 MATCH                                      → PASS
```

第 5 步放在阻塞项之前：学生把程序跑崩、跑超时，是确定的失败，不能因为
“因此没有观测、覆盖不全”而退化成 `INCONCLUSIVE`。

`grade_eligible` 与判定正交：后端未通过能力门禁时，`PASS`/`FAIL` 照常给出，
但 `grade_eligible=false` 并附 `EXECUTION_BACKEND_NOT_ATTESTED`；因此本机报告
永远不能用于正式评分。

## 8. 沙箱与能力门禁

- `SandboxBackend` 协议只有 `capabilities()`、`compile()`、`run()`，实现方
  不得在内部回退到宿主直跑。
- 本地后端用 Win32 Job Object 设置：单进程 CPU 时间、Job 内存与进程内存、
  活动进程数、CPU 硬上限、`KILL_ON_JOB_CLOSE`；进程以 `CREATE_SUSPENDED`
  创建，先加入 Job 再恢复线程，避免“先跑起来再限制”的竞态。
- 墙钟由宿主看门狗轮询；超时终止 Job；主进程退出后若仍有活动进程，终止整棵树。
- stdout/stderr 重定向到文件而不是管道，避免子进程写满管道阻塞。
- 环境变量最小化（`SystemRoot`、`WINDIR`、`PATH`、`TEMP`、`TMP`、
  `NUMBER_OF_PROCESSORS`），`TEMP` 指向本次工作目录。
- **能力门禁**：模板声明的必要能力逐项比对后端能力；缺失即拒绝执行。
  显式放行时仍标记 `attested=false`，报告写明“不得计入正式验收”。
- 已知边界：Job Object **不是**文件系统或网络隔离，不能让不可信代码读取教师
  机器上的文件或访问网络；正式部署必须叠加 Windows Sandbox 或固定虚拟机。

## 9. 存储与证据

- SQLite：`runs`、`run_events`、`artifacts`、`task_versions`、`calibrations`、
  `schema_meta`，WAL 模式。
- 每次运行目录：`plans/`（构建/测试/校验/请求）、`generated/`（本次构建源码）、
  `evidence/`（编译日志、每用例观测与原始输出、合成记录）、
  `objective_report.json`。
- 工件写入使用“临时文件 + fsync + `os.replace`”，避免读到半截 JSON。
- `replay` 只依赖 `evidence/`，用于审计与回归。

## 10. 本地 Web 界面（v0.2.0）

### 10.1 定位

Web 端只是 `interfaces` 层的一个入口，**不复制任何判定逻辑**：

```
浏览器 → FastAPI 路由 → RunOptions → execute_standard_run()（与 CLI 完全相同）
                                   ↘ data/runs/<run_id>/objective_report.json
         ← 报告页 / JSON / CSV ←──────┘
```

这样 CLI 与 Web 的结论、证据、退出码语义保持一致；Web 增加的能力只有“上传”、
“异步等待”与“浏览器展示”。

### 10.2 进程内执行模型

- `create_app()` 创建 `ThreadPoolExecutor(max_workers=1)`：一次只跑一个提交，
  后来的请求排队，符合实施方案“第一版单工作进程串行队列”的要求。
- 提交时先在内存中分配 `run_id`（`run_<时间>_<6hex>`）并立即 303 重定向到
  `/runs/<run_id>`，随后在线程里调用运行器。运行器支持传入预分配 `run_id`，
  并拒绝覆盖已存在的运行目录。
- 页面用 `GET /api/runs/<run_id>` 轮询；状态来源依次为：报告文件 → 进程内
  `pending`/`errors` → SQLite `runs.workflow_state`。
- `/runs/<run_id>` 在报告存在时渲染结果页，否则渲染等待页；运行失败时渲染错误页。

### 10.3 提交与安全边界

- 上传先写入 `data/web_uploads/<uuid>/`，限制 20MiB 与扩展名
  （`.zip`/`.cpp`/`.h`/`.hpp`），之后完全交给 `intake.ingest()` 做路径策略、
  压缩包成员校验、大小与文件数限制——Web 层不自行解压。
- 表单只接受 `task_ref`、`variant`、`submission`、`target_before`；
  `variant` 只允许任务包 `reference_suite.json` 中声明的 ID。
- 任务页**不渲染用例输入与预期值**，只展示规则、操作、断言 ID 与 `purpose`，
  避免学生针对用例硬编码。
- Jinja2 默认自动转义；CSV 下载带 UTF-8 BOM 并复用 `guard_cell()` 防公式注入。
- 默认只监听 `127.0.0.1`；`--host` 改为非回环地址时启动会打印警告。当前没有
  登录、鉴权与多用户隔离，属于本阶段的明确边界。
- 取消：`POST /runs/<run_id>/cancel` 写入 `CANCEL` 文件，运行器在阶段/用例边界
  检查；Web 不直接终止线程。

### 10.4 路由

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/` | 题库、最近运行、后端能力横幅 |
| GET | `/runs` | 运行列表（SQLite） |
| GET | `/tasks/{task_ref}` | 任务详情与两个提交表单 |
| POST | `/runs` | 创建运行（variant 或上传） |
| GET | `/runs/{run_id}` | 等待页 / 结果页 |
| GET | `/api/runs/{run_id}` | 状态 JSON |
| POST | `/runs/{run_id}/cancel` | 写取消标记 |
| GET | `/runs/{run_id}/report.json` | 报告 JSON |
| GET | `/runs/{run_id}/report.csv` | 报告 CSV |
| GET | `/healthz` | 健康检查 |

### 10.5 测试

`tests/unit/test_web.py` 用 `TestClient` 覆盖：首页/任务页渲染、用例输入不外泄、
`variant=correct` 得到 PASS 且能下载 JSON/CSV、`variant=faulty` 得到 FAIL
（真实 `g++` 后端，mock 后端会按 expected 合成观测、测不出缺陷）、缺提交与未知
任务/运行的错误码、取消标记落盘。

### 有意简化

1. **题库规模**：5 题 26 用例，而非最终 10 题 40 用例；生成器已按可扩展方式组织。
2. **任务包目录**：未单独建 `reference_verifier/adapter|observer` 子目录，
   仅保留 `reference_verifier/assertions.json`（已验判断程序）与说明文件。
3. **观测提取**：本期统一由标准输入输出驱动输出结构化 `actual`，未实现
   “原始文本 + 声明式解析器”的第二条路径；解析与比较仍然分离。
4. **提交匹配**：相对路径优先、基本名唯一兜底，未做完整的工程结构语义校验。
5. **校验等级**：运行期通过全部检查记为 `CHECKED`；`CALIBRATED` 由校准工具
   记录在任务版本表，尚未回写到单次报告。

## 12. 扩展到模式二的接入点

模式二（LLM 生成目标程序）可以直接复用：

- `IOTemplate` 与 `TestMethodSpec`：告诉 LLM“怎么选输入、调什么、观察什么、断言什么”；
- `ReferenceVerifier`（已验判断程序）：作为 few-shot 样例与正确性锚点；
- `ReferenceSuite` 与校准工具：验证 LLM 生成的判断程序；
- `BuildPlan`/`TestPlan`/`Observation`/`CaseResult`/聚合器：执行与判定内核不变；
- 预留模型 `TargetVerifierBundle`、`AdapterBundle`、`BindingMap` 已定义但未实现，
  模式二需要新增 `llm`、`planning`、`analysis` 三个包并接入工作流状态
  `ANALYZING → ADAPTING → PROBING → CALIBRATING → FROZEN`。

新增 LLM 时务必保持：诊断报告与客观测试报告分开保存；LLM 输出只作为建议，
不得写入 `assessment_status` 或 `grade_eligible`。
