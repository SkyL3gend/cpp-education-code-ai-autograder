# 阶段性总结（v0.5.1，2026-10）

> 面向 C++ 程序设计教学的代码小改自动测评与 AI 诊断系统 —— 当前实现到哪一步、
> 哪些经过真实验证、离任务书验收还差什么。

## 1. 项目目标

按《工程实践项目任务书》与《双模式测评系统架构与实施方案》，系统要接收学生提交的
C++ 程序，针对一道“代码小改题”判断是否合格，并给出可复核的证据；LLM 只参与
**适配与诊断**，不能直接决定分数。

任务书四项任务：

| 任务 | 要求 | 当前状态 |
| --- | --- | --- |
| 任务 1 | 接收程序/工程，测试用例与测评程序分离，至少支持标准输入输出型测试，不可信提交隔离执行 | 已完成（隔离等级不足，见 §7） |
| 任务 2 | ≥10 道题、每题 ≥4 用例；正确实现通过、已知缺陷被识别 | 部分完成（5 题、26 用例，校准通过） |
| 任务 3 | LLM 只做诊断与审批，程序正确性由测试用例判定 | 部分完成（“判定与 LLM 分离”已实现；**诊断报告未实现**） |
| 任务 4 | Web 选题/提交/看结果/请求诊断/导出 | 部分完成（选题/提交/结果/导出/批量已完成；请求诊断未做） |

验收口径还差：10 题 × 4 用例、10 份诊断评价材料、更严格的隔离后端。

## 2. 已完成的能力

### 2.1 模式一：基准工程路径（确定性判分）

- 五个任务包（`task_library/tasks/t1…t5/1.0.0/`），每题含规则、输入/输出 Schema、
  测试方法、用例、断言、正确/缺陷参考实现、校准记录。
- 提交形态：按相对路径覆盖基准工程；支持整个文件夹（自动剥一层顶层目录）、
  ZIP、单个完整 `.cpp`。找不到基准文件时不再拒绝，转“单文件适配（观察型）”。
- 流水线：校验 → 构建计划/测试计划冻结 → 编译 → 受限执行 → 标准输入输出协议
  取结构化观测 → 宿主侧断言（`EQUALS`/`MULTISET_EQUALS`/`UNCHANGED`）→ 聚合 →
  `objective_report.json` + 原始 stdout/stderr/编译日志等证据 → `replay` 可复现。
- 判定与状态正交：`execution_status × assessment_status × comparison × termination`；
  退出码 0/1/2/3/4/130 分别对应 PASS/FAIL/NOT_ASSESSED/INCONCLUSIVE/基础设施错误/取消。
- 能力门禁：本机 Job Object 后端缺网络/文件系统隔离，`grade_eligible` 恒 `false`，
  报告写明原因；不会把“环境不够”伪装成学生通过。

### 2.2 模式二：LLM 适配（v0.5.0 起）

- 模型读任务契约 + 目标程序源码，产出**声明式** `TargetVerifierBundle`：
  编译方式、驱动（`stdin_script` / `function_driver`）、观测提取器与参数、
  断言绑定、迁移矩阵、覆盖缺口。
- 宿主四道闸门：静态校验（Schema、占位符、断言绑定、迁移矩阵、禁止期望值字段）→
  编译与探针试跑 → 有界修正（最多 2 轮，只许改适配层）→ 冻结执行正式用例。
- 正式判定仍走模式一同一套断言与聚合；报告标注 `mode=LLM`、`validation_level=CHECKED`，
  附 `plans/migration_matrix.json` 与 `target_bundle.json`。
- 适配失败/观测不到时归因 `ADAPTATION_FAILED`/`INCONCLUSIVE`，明确“不是学生程序的错”。
- 支持菜单程序预置数据：`driver.seed_session` 按用例 `initial_contacts` 重建前置联系人，
  使生日提醒、检索类题目可判；支持逐用例剧本 `session_by_case`。
- Web：首页“LLM 模式”已开放，页面填 Key 即可；Key 只走请求内存/环境变量/
  仓库外 `%USERPROFILE%\.cpp-assessor\llm.env`，日志脱敏，仓库零残留。
- 可移植技能包：`skills/cpp-microchange-judge-author/SKILL.md`（给外部模型/工具读的
  任务说明与输出契约）。

### 2.3 教学界面与批量

- 模式选择页（基准模式 / LLM 模式）、中英双语（只翻译展示层，枚举代码不变）、
  `Accepted · 通过` / `Rejected · 未通过` 徽章。
- 批量测评：一次最多 10 个程序 × 5 道题串行矩阵；每个上传物落成
  `programs/<id>/source/` + 预留 `verifier/`，ZIP 与单文件可混批，可取消/可恢复。
- 结果页：结论、状态、逐用例断言、覆盖、观察说明、证据链接、JSON/CSV 导出。

### 2.4 基准程序实测（selfcheck）

- 对附带的参考程序做真实编译与脚本化菜单驱动，观察 5 条检查并给出
  `PASS`/`DEFECT`/`NOT_OBSERVED` 与证据；明确是“行为观察”，不参与五题评分。

## 5. 关键设计决策（以及为什么）

1. **评分靠接口，实测靠界面**：五题正式判分依赖任务包声明的接口/协议，不依赖学生
   界面文案；菜单脚本只用于“观察型”适配与基准程序实测，锚点对不上就报未观测到。
2. **LLM 不判分**：模型只输出“怎么观察”的声明，断言、期望值、聚合全在宿主；
   模型看不到私有期望值，输出里出现 `expected`/`answer` 等字段直接拒绝。
3. **宁可 `INCONCLUSIVE` 也不猜**：适配失败、观测不到、编号不可比，都如实报告并
   归因给适配层，不算学生错；这是任务书“不能以 LLM 判断作为评分依据”的延伸。
4. **单文件不再拒绝**（0.4.1）：整程序是学生常见提交形态，改为编译后用固定菜单
   脚本观察一条规则，并明确“观察型、不是完整评分”。
5. **菜单程序用 `seed_session` 预置数据**（0.5.1）：与其假装初始联系人是“程序自带
   数据”，不如按用例声明重建，保证断言可核对。
6. **T5 不硬凑**：初始编号在菜单程序里不可表达，硬归一化会掩盖缺陷，选择记
   `INCONCLUSIVE`，等函数级驱动或任务包声明映射策略再解决。

## 6. 当前限制与风险

1. **隔离等级不足**（最高优先级工程风险）：本地 Job Object 不能阻断网络与文件系统
   访问，`grade_eligible` 恒 `false`；需要 Windows Sandbox/虚拟机后端才能正式评分。
2. **AI 诊断缺失**：任务 3 的“错误定位 + 修复建议 + 教师审批”尚未实现，目前只有
   客观测评报告；验收要求的 10 份诊断评价材料无从产出。
3. **题库规模**：5 题 26 用例，任务书要求 ≥10 题、每题 ≥4 用例。
4. **模式二依赖模型**：清单有随机性；T1—T4 已校准，T5 只能到 `INCONCLUSIVE`；
   结构特别自由的程序仍可能 `ADAPTATION_FAILED`。
5. **Web 无鉴权/多用户隔离**，上传不自动清理；班级与成绩管理未做。
6. **批量串行**：10×5 上限，单工作线程；题量上去后需要并行与队列。
7. **模板能力未用满**：动作前观测与 `UNCHANGED` 断言已实现，但五题未使用。

## 7. 下一步建议（按优先级）

**P0（验收硬缺口）**

1. 实现 AI 诊断模块：输入客观报告 + 代码 + 任务规则，输出错误定位、规则依据、
   修复建议；教师审批后另存，**不改变** `assessment_status`；Web 加“请求诊断”页。
2. 扩题到 10 题（补 5 题、每题 ≥4 用例），跑 `tools/calibrate.py` 校准正确/缺陷实现。
3. 产出 10 份诊断评价材料（诊断报告 + 教师审批记录 + 与自动判定的一致性核对）。

**P1（可信度）**

4. 接 Windows Sandbox 或固定虚拟机后端，过能力门禁，让 `grade_eligible` 可为 `true`。
5. T5 的初始编号方案：要求程序支持函数/文件导入初始数据，或任务包声明编号映射。
6. 模式二提示词与提取器的回归集：把 T1—T4 的清单固化为样例，换模型时自动比对。

**P2（工程化）**

7. Web 鉴权、上传清理、批量并行；`verifier/` 目录接每程序专属判定代码。
8. 文档收尾：把本总结并入实验报告/答辩材料，补部署与运维说明。

## 8. 复现入口

```powershell
# 测试
python -m pytest

# 模式一（基准工程路径）
python assessor.py run --task t1_phone_validation@1.0.0 --submission path\to\submission.zip --backend local --allow-unattested-backend

# 单文件完整程序（观察型适配）
python assessor.py run --task t1_phone_validation@1.0.0 --submission "参考基准程序\通讯录_v6最终版.cpp" --backend local --allow-unattested-backend

# 模式二（LLM 适配；Key 由环境变量或仓库外 llm.env 提供）
python assessor.py run --task t1_phone_validation@1.0.0 --submission "参考基准程序\通讯录_v6最终版.cpp" --llm --backend local --allow-unattested-backend

# Web
python assessor.py web --allow-unattested-backend
```

- 报告与证据：`data/runs/<run_id>/`（`objective_report.json`、`plans/`、`evidence/`）。
- 批量：`data/batches/<batch_id>/batch.json` 与 `programs/<id>/`。
- Key 配置：环境变量 `ASSESSOR_LLM_API_KEY`，或仓库外
  `%USERPROFILE%\.cpp-assessor\llm.env`；仓库内不保存任何 Key。
