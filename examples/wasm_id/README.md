# 编号分配试测样例

- `id_correct.cpp` / `id_correct.zip`：新增时扫描当前联系人编号，按作者实现分配当前最大编号加一；空通讯录从 1 开始。
- `id_faulty.cpp` / `id_faulty.zip`：故意用“当前条数加一”分配编号，删除后或已有大编号时会给出错误编号，甚至与仍占用的编号重复。

文件由 `contactbook_base@1.0.0` 与 T5 correct/faulty 变体组合而成。本题替换 **`contactbook.cpp`**，`validators.cpp` 来自基础工程。单文件按 `validators.h`、`contactbook.h`、`validators.cpp`、`contactbook.cpp` 顺序合并，仅去掉本地头文件包含和 `#pragma once`，没有 `main()`。ZIP 保留这四个平级原文件，已校验来源字节、CRC 与安全路径。

在支持 T5 的新版 `wasm_pilot` 服务选择“编号分配”，上传任一 `.cpp` 或 `.zip`。LLM 应生成驱动，按输入操作顺序真实调用 `removeById`、`addContact` 并读取 `contacts()`；输出实际存储顺序的 `id_list` 与完整 `contacts_after`。不能排序、去重、补算编号或隐藏重复 ID，也不能只输出新分配的一个编号。

正确单文件与缺陷 ZIP 均从独立解压包完成新真实 LLM 测评。正确运行 `run_20261024_182906_4062eb` 得到五项正式、八项补充全部符合，完整活动 73.58 秒；缺陷运行 `run_20261024_183048_4d45de` 为正式两项符合三项不符、补充三项符合五项不符，91.45 秒。两次均通过 26 次独立夹具回归，各十三份有序 ID 与完整记录观测已逐项核查。

缺陷版实际在删除中间后返回 `[1,3,3]` 而应为 `[1,3,4]`；大编号导入后为 `[5,9,3]` 而应为 `[5,9,10]`；删除后连续新增为 `[2,2,3]` 而应为 `[2,3,4]`。这三项编号列表及通讯录断言都不符，空通讯录和删除不存在编号两项符合。

八项补充覆盖非排序初始编号、首/中/末项删除、连续新增、无效删除和清空，独立于正式五项计数；正确单文件八项符合，缺陷 ZIP 三项符合五项不符。判断程序仍为 `CHECKED`、`grade_eligible=false`。

作者规则基于**当前**最大编号，不是永久保存历史最大值：删掉最高编号后可按剩余当前最大值加一，清空后可重新从 1 开始，不能据此误判缺陷。其他函数保持基础工程实现，这组样例仅用于 T5，旧版只含前四题的便携包需要更新。试验结果不能直接作为正式成绩。
